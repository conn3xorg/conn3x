# Roadmap

The full roadmap lives at [docs.conn3x.org/roadmap](https://docs.conn3x.org/roadmap). This is the short version. There are no dates, and nothing here works until a [release](https://github.com/conn3xorg/conn3x/releases) says it does.

The goal: anything you'd do with Terraform, OpenTofu, Ansible, Chef or Puppet, you'll be able to do with Conn3x.

## Today

- Linux hosts: Rocky Linux, RHEL, AlmaLinux, Fedora, Debian and Ubuntu, tested on every change.
- Windows Server 2022 and 2025 over OpenSSH, in preview: files, access rules, registry, services, features, users and groups, firewall rules, MSI packages, scheduled tasks and IIS, with a tested [Azure example](examples/azure-windows-server). A circuit can also build a small Active Directory domain: set a server's DNS servers, make it the first domain controller of a new forest, and, since v0.7.2, join other servers to the domain and promote a member to another domain controller, and since v0.7.3, keep the OUs, groups and users inside it. Since v0.11.0 it can add a child domain, and a group can take members from other domains in the forest. The [azure-domain example](examples/azure-domain) builds the forest, joins a server to it, and creates an OU, a user and a group with that user in it. Since v0.19.0 all 25 Windows modules are out of experimental, a domain can grow a new tree, and group members can come across a forest trust.
- Databases, since v0.11.0: `postgresql_database`, `postgresql_role`, `mysql_database` and `mysql_user` steps, with exact grants, and passwords that never travel as plain text. Since v0.14.0, a role's grants on databases, schemas and tables are its whole list, and what isn't listed is revoked.
- `confirm_after`, since v0.11.0, on `file`, `template`, `ufw` and `firewalld` steps: if a change cuts Conn3x off, the host puts it back by itself.
- 127 official circuits, from nginx and PostgreSQL to k3s, Suricata and a private AI stack, in the [catalogue](https://docs.conn3x.org/circuits).
- The [Circuit Builder](https://conn3x.org/build), which writes a config from the circuits you pick, with host roles, an optional step that creates the servers too, and a link you can share.
- Adopting servers you already run: `import` on a step takes over what a Linux host already has, on 21 modules since v0.9.0, from `file` and `package` to `cron`, `mount` and firewall rules, and on the database steps since v0.11.0, and steps take OpenTofu's `lifecycle` block, from `prevent_destroy` to preconditions. `provider::conn3x::import_id` adopts what a shared circuit manages, and `conn3x generate step` writes the step from what's on the host. See [Adopt servers you already run](https://docs.conn3x.org/guides/adopt-servers).
- Steps that own the whole of something, since v0.14.0: a user's crontab (`crontab`), a host's package sources (`package_sources`), a user's `authorized_keys` (`exclusive = true`), and owner and mode on a whole tree (`directory` with `recurse = true`).
- TLS on the host, since v0.15.0: `tls_private_key`, `tls_self_signed_cert` and `tls_csr` make keys, certificates and signing requests with the host's own `openssl`, and a private key never reaches state.
- Ansible's error handling, since v0.16.0: `rescue` blocks run where a watched step failed, `always` blocks run either way, and `prereq` blocks run before a step only where it's about to change.
- Disks, containers and more, since v0.16.0: `filesystem`, `lvm_volume_group`, `lvm_logical_volume`, `container` (Docker or Podman), `nm_connection`, `sudoers` and `modprobe`.
- Secrets that stay out of state, since v0.16.0: SSH keys from ephemeral values with the provider's `private_keys`, and SOPS files through `ephemeral "conn3x_secrets"`.
- `strategy = "per_host"`, since v0.9.0, so a slow host doesn't hold up the others. Since v0.15.0, `-limit` runs a circuit on some hosts only, `batch_size` and `max_failures` roll it out a few hosts at a time, and `on` runs a step on another host.
- Arista EOS switches over their own CLI, experimental since v0.9.0: `eos_config`, `eos_hostname`, `eos_vlan`, and since v0.10.0 `eos_interface` and `eos_user`, with one session and one commit per switch, tested on cEOS-lab, not yet on hardware. See [Network devices](https://docs.conn3x.org/network-devices). Since v0.13.0, circuits on one switch take turns at its config session, so one commit never makes another circuit's lines live.
- Juniper Junos over its own CLI, experimental since v0.17.0: `junos_config`, `junos_hostname`, `junos_vlan`, `junos_interface` and `junos_user`, with a dry run before every commit, one `commit confirmed` per device per circuit and a confirm over a new login, tested on vJunos-switch, not yet on hardware.
- VyOS over its own CLI, experimental since v0.18.0: `vyos_config`, `vyos_hostname` and `vyos_interface`, with a dry run before every commit, one `commit-confirm` per router per circuit and a confirm over a new login, tested on a VyOS rolling container, not yet on hardware.
- Steps for the jobs that used to be a `command` with curl or sed, since v0.19.0: `uri` for an API call from the host, `wait_for` with a `url`, `json_value` and `xml_value` for one value in a config file, `acl` and `package_hold`.
- Hosts with no open SSH port, since v0.20.0: `proxy_command` carries the connection over AWS Session Manager, Google Cloud IAP or any command, as OpenSSH's `ProxyCommand` does, with host keys still checked. `ios_config` reaches Cisco IOS XE and, with `legacy_algorithms`, classic IOS, experimentally. New steps cover `nftables`, `partition`, `swap`, `selinux_mode` and `ssh_keypair`.
- The package managers that aren't apt or dnf, since v0.21.0: `snap`, `flatpak` and `npm` steps, `debconf` for a Debian package's install-time answers and `alternatives` for which `java` or editor a host runs. `conn3x_host` reads the facts a host keeps about itself, Ansible's `facts.d` included, and on Arista EOS `become` reaches privileged mode through `enable`.
- Ansible roles that keep their per-OS values in files per release, since v0.22.0: `Ubuntu-24.04.yml` beside `Debian.yml`, and several `include_vars` layered or switched by family, picked at plan from each host's facts. A handler takes a `when`, and the release tag is signed with gitsign.
- Containers as hosts, experimental since v0.23.0: `container` in the `ssh` block or a host object runs every command with `podman`, `docker` or `kubectl exec`, with no sshd. The same release gives the edit steps `validate`, `mode`, `owner` and `group`, and `conn3x convert ansible` reads loops over lists of maps.
- Ansible per-OS values that only some releases set, since v0.24.0: the steps that read one stop at plan on a host whose release has none, as Ansible does, and a package list from a default or `vars/` becomes a step per item. The same release writes a role's text into the circuit as HCL strings ([GHSA-vw46-5wwm-wc8g](https://github.com/conn3xorg/conn3x/security/advisories/GHSA-vw46-5wwm-wc8g)).
- Editors beyond VS Code, since v0.25.0: `conn3x lsp` is a language server with module and argument completion, hover docs and `conn3x validate` on save, experimental. `-limit` takes `=name` for one host by its exact name, and `CONN3X_SSH_SHELL=1` tries a long-lived shell per SSH session slot to cut round trips.
- Modules you write yourself, since v0.26.0: a `script` step runs a program from the circuit's directory, in any language the host has, that speaks JSON in four modes, and Conn3x keeps its plan, state and drift. Experimental. `backup = true` on `file`, `template` and the edit steps keeps a copy of a file before a step changes it.
- Bringing a fleet in, since v0.27.0: `conn3x each plan` plans every root configuration in dependency order, or only those a change touched; `generate steps` lists the packages someone installed and the cron jobs already running; a `selinux_port` step, `masked` services, `backrefs` on `line`; and `conn3x convert ansible` converts `seport`, `openssh_keypair` and `win_share`.
- The tasks a conversion still left as TODOs, since v0.28.0: most of them now convert, from a repository added the modern way to a switch's VLANs. `package` reaches Alpine and SUSE hosts, and `repository` SUSE. New steps include `fetch`, `supervisor_program`, `htpasswd`, `ufw_settings`, `container_image`, `container_network` and `container_volume`, and eight for Windows. Cisco IOS XE gets `ios_hostname`, `ios_interface`, `ios_vlan` and `ios_static_route`, and Arista EOS gets `eos_static_route`, experimental: they're tested against parsed device configurations, and the run on a real device is still to come ([#1174](https://github.com/conn3xorg/conn3x/issues/1174)).
- Jobs a conversion had no step for, since v0.29.0: `patch` applies a patch and keeps it applied, `pack` packs files into a tar, compressed tar or zip archive, and `compose_project` keeps a Docker Compose or podman-compose project up, stopped or down; `conn3x convert ansible` turns `patch`, `archive` and `docker_compose_v2` tasks into them. `service_action` gains `try-restart` and `try-reload`, which leave a stopped unit stopped, and a lone `daemon-reload`.
- Two more jobs a conversion left for review, since v0.31.0: `iptables_rule` keeps one iptables or ip6tables rule in a chain and can save it to load at boot, and `pam_rule` keeps one rule in a PAM service file, leaving comments and `@include` lines as they were; `conn3x convert ansible` turns `iptables` and `pamd` tasks into them. Validate now names a read-only attribute that was given a value.
- Ephemeral secrets refused where they'd be kept, since v0.33.0: a value from `conn3x_secrets`, `conn3x_hostdata` or `conn3x_ssh_tunnel` passed to an ordinary argument stops validate, instead of being written to the saved plan and state. A `git` step checks out submodules with `submodules = true`, and `conn3x convert ansible` sets it from `recursive`.
- Files copied on the host, since v0.34.0: `source_path` on a `file` or `windows_file` step copies a file that's already there, hashed on the host so its content stays out of the plan and state, and `conn3x convert ansible` turns `copy` and `win_copy` with `remote_src: true` into them. A `container` step takes `user`, `labels`, `memory`, `cpus` and log settings, and `confirm_after` puts a removed iptables or ufw rule back at the position it held.
- Packages from a file or a repository that's off, since v0.35.0: a `package` step installs a `.deb` or `.rpm` already on the host with `source`, and takes `enable_repositories` for CRB and the like and `target_release` for Debian backports. A `ufw` step allows an application profile with `app`, `ufw_settings` sets `logging`, and `conn3x convert ansible` converts `script`, `stat` probes, `cron_file`, `win_environment` and the Python bootstrap a playbook no longer needs.
- Real Galaxy roles further through `conn3x convert ansible`, since v0.36.0: a role default that sets a service's state, enables a repository or builds on another default becomes a variable you can change, host facts work inside arguments, `include_tasks` behind a family, codename or probe is followed, and an `ansible_version` test is read as ansible-core 2.16 or later. `conn3x_host` reports `os_codename` and `service_manager`, and `source_sha256` on a `package` step upgrades a downloaded `.deb` or `.rpm` in one apply.
- Restarts in the middle of a circuit, since v0.37.0: `service_action` runs a oneshot unit with `action = "start"` and clears a start limit with `reset_failed`, with the same retry through a systemd re-exec as its other actions, and `wait_for` and `windows_wait_for` take `triggers`, so a wait after a restart waits again. A `package` step downgrades on apt to a pinned `version`, and `conn3x convert ansible` reads `allow_downgrade` and `creates=`, `removes=` and `chdir=` written inside a command line.
- Directories copied to hosts, since v0.17.0: `directory_copy` writes only the files that differ and names them in the plan.
- `conn3x convert ansible` for bringing playbooks and, since v0.9.0, local roles across, and since v0.11.0 the roles a playbook runs, with their dependencies, and since v0.12.0 database tasks, `win_updates`, `tasks_from` and a role in a `loop`, since v0.13.0 a role call in an imported task file, since v0.14.0 `exclusive` keys, `recurse` and PostgreSQL database grants, since v0.15.0 `delegate_to`, `serial` and OpenSSL keys and requests, since v0.16.0 `block`/`rescue`/`always`, the storage and container modules and roles straight from Galaxy, and `conn3x drift` for both layers.
- Ansible inventories, since v0.16.0: `provider::conn3x::inventory` reads INI or YAML with `group_vars` and `host_vars`, and `conn3x run` runs one command or module on a group of hosts without a circuit. Since v0.18.0, `provider::conn3x::hostdata` looks values up layer by layer, as Hiera does, and `conn3x run -task` runs a named set of steps on each host, as a Bolt task does.
- Reading a host at plan, since v0.18.0: `data "conn3x_file"` and `data "conn3x_command"`, and `ephemeral "conn3x_ssh_tunnel"` for another provider to reach what only the host can.
- Any OpenTofu provider. AWS, Azure, Google Cloud and DigitalOcean are tested end to end, each with a [tutorial](https://docs.conn3x.org/tutorials).

## Now

Windows at scale. A forest, member servers, more domain controllers, and the OUs, groups and users in the domain work, and the [azure-ad-lab](examples/azure-ad-lab) example builds a whole domain from one config. Since v0.9.0, [azure-windows-fleet](examples/azure-windows-fleet) builds a domain controller and up to five IIS servers from one apply. Twenty Windows servers in one apply have run on Azure. Since v0.19.0 all 25 modules are out of experimental and 21 take `import`, the forest, domain controllers and domain members among them. Promoting a domain controller straight from a workgroup server, child domains and new trees, the `ou` argument on a join, and group members from another domain in the forest and across a forest trust have all been tested on Azure, and so has Windows Update bringing an eight-month-old server current. What's left is scale: more hosts in one apply, and Windows as a whole out of preview.

## Next

Network devices over their own CLI, starting with Arista EOS: switches, routers and firewalls, in the same plan as the hosts behind them. The first three device circuits are already out, and they're experimental: [RouterOS baseline](https://docs.conn3x.org/circuits/routeros-baseline), [OPNsense VLANs](https://docs.conn3x.org/circuits/opnsense-vlans) and [Proxmox VE network](https://docs.conn3x.org/circuits/proxmox-network). They go through community OpenTofu providers and were tested on virtual images, not hardware. Since v0.9.0 Conn3x talks to Arista EOS itself, experimentally; since v0.10.0 every step on a switch shares one session and one commit, and `eos_interface` and `eos_user` are out. Junos joined it in v0.17.0, and VyOS in v0.18.0. Classic Cisco IOS is next.

## After that

- A web UI: a self-hosted, open-source app for teams to run plans and applies, approve them, see history, schedule drift checks and keep credentials per project, in the spirit of [Semaphore UI](https://github.com/semaphoreui/semaphore) and AWX.

More circuits come alongside, when people ask for them.

## Toward full IaCC

The rest, in order. The full roadmap says where each one fits among the items above.

- The rest of OpenTofu on host steps. `import` and `lifecycle` on steps shipped in v0.8.0, and import on the rest of the Linux modules in v0.9.0; what's left is import on Windows.
- Rolling updates and orchestration: batches with a failure limit, run-once and delegated steps, tasks and plans that chain them, like Bolt's, have all shipped; what's left is running them from the web UI.
- Servers that keep themselves right: scheduled applies from the web UI, run reports and host facts you can search, then a pull mode.
- Encrypted variable files you can commit, like Ansible Vault.
- Compliance checks that only report, a test command on containers, and policy on plans.
- Your own modules, converters for Chef cookbooks and Puppet modules, and a circuit registry.
- Runs that start on an event, such as an alert or a webhook.

## Later

macOS hosts.
